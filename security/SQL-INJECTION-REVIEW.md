# Заключение о проверке SQL-инъекции

**Дата: 9 ноября 2026 года.**

**Исследованная версия:** `4903ad261d30bc2d1171e455f916e445a7963b4e` [выданного приложения](https://devsecops.gitlab.yandexcloud.net/devsecops-projects/unit-9-final-practice/-/tree/4903ad261d30bc2d1171e455f916e445a7963b4e).

По результатам ручного анализа предоставленных исходников **SQL-инъекция в исследованной версии репозитория не обнаружена**. Вывод основан на следующих фактах.

1. **В `app/crud.py` пользовательские значения передаются через параметры `$1`, `$2`, `$3`.** Проверка владельца счёта, чтение и изменение остатка, создание транзакции выполняются с передачей значений отдельными аргументами методов `asyncpg`. Основание: строки 8–10, 22, 28, 32–37 [исходного файла](../app/crud.py).
2. **В функции `list_transactions()` поисковая строка не вставляется в SQL-текст.** Выражение `params.append(f"%{search}%")` формирует значение параметра, которое затем передаётся через `conn.fetch(sql, *params)`. Поэтому кавычки, `OR 1=1` и другие SQL-конструкции внутри `search` обрабатываются как содержимое поискового значения и не меняют структуру запроса. Основание: строки 58–66 [исходного файла](../app/crud.py). Такой способ параметризации соответствует [документации asyncpg](https://magicstack.github.io/asyncpg/current/usage.html).
3. **Использование форматируемых строк при сборке SQL здесь не создаёт инъекцию.** В выражениях `ILIKE ${i}` и `LIMIT ${i}` подставляется только номер параметра. Переменная `i` задаётся внутри функции и не контролируется пользователем. Основание: строки 59–64 [исходного файла](../app/crud.py).
4. **В `app/db.py` используются фиксированные SQL-запросы** для создания таблиц и начального заполнения; пользовательские данные в них отсутствуют. Основание: строки 15–36 [исходного файла](../app/db.py).

В проверенных SQL-вызовах пользовательские значения отделены от текста запроса. **SQL-инъекция в исследованных путях обработки данных не обнаружена.** Подмена личности и ошибки денежных операций рассмотрены отдельно в итоговом отчёте.

## Полнота проверки SQL-вызовов

| Место | Операция | Как отделены данные от SQL |
|---|---|---|
| `app/crud.py:8–10` | Проверка принадлежности счёта | `account_id` и `user_id` передаются отдельно для `$1` и `$2` |
| `app/crud.py:22` | Чтение остатка | `from_id` передаётся для `$1` |
| `app/crud.py:28` | Проверка счёта получателя | `to_id` передаётся для `$1` |
| `app/crud.py:32–33` | Списание и зачисление | Сумма и номер счёта передаются для `$1` и `$2` |
| `app/crud.py:35–37` | Запись перевода | Два номера счетов и сумма передаются для `$1`, `$2`, `$3` |
| `app/crud.py:52–66` | Поиск истории | Текст строится из постоянных частей и внутреннего счётчика; владелец, поиск и предел передаются в `params` |
| `app/db.py:15–36` | Создание таблиц, подсчёт и начальное заполнение | Постоянный SQL без пользовательских значений |

Других мест выполнения SQL в семи файлах `app/*.py` не обнаружено. Строка подключения `POSTGRES_DSN` является настройкой окружения и не формируется из HTTP-запроса. Команды Redis не являются SQL-запросами.

## Сопоставление с результатами проверок

В [исходном отчёте Semgrep](reports/semgrep.json) есть два предупреждения о динамическом SQL в `app/crud.py:61,64`. При ручном разборе оба предупреждения признаны ложными срабатываниями: в текст попадает внутренний номер параметра. Отдельное правило отслеживания поисковой строки до текста запроса не сработало. Третье срабатывание относится к проверке личности, а не к SQL.

В [журнале проверки поведения](reports/behaviour.json), раздел `sql_injection`, сохранены запросы и значения параметров для шести строк поиска: с логическим условием, объединением выборок, удалением таблицы, вызовом задержки, а также `%` и `_`. Структура запросов не изменилась, чужая исходящая история не раскрылась, таблица счетов сохранилась. Результаты согласуются с анализом параметризованных SQL-вызовов.

Первоначальные проверки выполнены прямыми вызовами функций версии `4903ad2` на отдельной PostgreSQL. Контрольные суммы этой версии приведены в [сведениях о проверке](reports/provenance.json).

## Проверка работающего приложения

Для испытаний через HTTP исправлены импорты `app/main.py` и добавлен `Dockerfile`. SQL-запросы не менялись. На отдельном стенде выполнены 47 запросов, включая:

- обычные переводы и поиск собственных и чужих операций на непустой истории;
- семь строк с SQL-конструкциями в `search` для каждого из двух владельцев;
- шаблоны `%` и `_`;
- SQL-строки в заголовке личности, пределе выдачи и числовых полях перевода;
- контрольные запросы после попыток инъекции и отдельную проверку подмены пользователя.

SQL-конструкции в поиске не раскрыли чужие операции. Недопустимый заголовок отклонён с HTTP 400, некорректные числовые поля — с HTTP 422. Счета, остатки и переводы до и после попыток SQL-инъекции полностью совпали. Подмена пользователя проверена после этой сверки и подтверждена как отдельная уязвимость.

**SQL-инъекция через проверенные HTTP-запросы не подтверждена.** Существующая параметризация сохранена; исправлений SQL не потребовалось. Результаты: [журнал HTTP-проверки](reports/http-behaviour.json), [повторный отчёт Semgrep](reports/semgrep-http.json). Команды запуска приведены в [инструкции](REPRODUCE.md).

## Разграничение с другими недостатками

- Символы `%` и `_` меняют шаблон поиска `ILIKE`, но не становятся SQL-кодом и не отменяют условие владельца.
- Подмена `X-User-Id` позволяет выбрать чужую личность. Это ошибка проверки личности с последствиями для доступа к объектам, а не SQL-инъекция.
- Одновременное списание сверх остатка и повтор перевода после отказа Redis относятся к денежной логике и обработке сбоев.

Описание этих недостатков и меры защиты приведены в [итоговом отчёте](REPORT.md).
